# 設計メモ

## なぜこの形か

告示データの不在は「誰も作っていない」ではなく「作る側の正確さ基準では
割に合わない」ことに起因する、というのが実測から得た見立てである。
溶け込み済みの現行文を保証しようとすると、改正の適用・廃止の判定・
図表の再現まで必要になり、国の検討でも前に進んでいない。

本パイプラインは基準を変える。要件は「正確に確定したデータ」ではなく
「辿れる材料を一次情報源から集め、出典つきで並べること」。
現行かどうか・改正がどう効くかの読み解きは、利用側（人間／AI）の仕事として残す。
その代わり、材料の同一性（どの告示か）と出典（どこで原本を確認できるか）は
厳密に管理する。

## 同一性と正規化

- ID = `発出者キー - 西暦年 - 告示番号`。告示番号は年度ごとに振り直されるため
  年まで含めて初めて一意になる
- 番号表記は資料ごとに揺れる（アラビア数字／全角／漢数字の命数表記／
  一〇二四式の位取り表記）。`common.kanji_to_int` で統一する
- 共管告示（例: 厚生労働省・国土交通省・環境省告示）は発出者を
  `joint-...` として保持する
- 情報源間で同じIDになったレコードは統合し、情報源を併記する

## 情報源ごとの癖（実測）

- Excel一覧: 全5,295件（うち告示1,043件）。住宅局の行は2019-03が最後で、
  以後は他部局分だけが更新されている。歴史側の母集団としては有用だが、
  2017年・2018年も住宅局分は薄く、「一覧にある＝全部」ではない
- 住宅局ページ: 制定・改正の告知であり在庫一覧ではない。見出しの日付は
  公布日（施行日併記あり）。まれに旧告示の再掲・参照が混ざり、見出し年と
  告示番号の年が食い違う場合は、日付を未確定として `date_note` に残す
- 両情報源はほぼ素集合だった（統合456件中、両方に載るものは0件）。
  交わらないこと自体が、それぞれの掲載基準の違いを示している
- 官報: 無料公開は直近90日分のみ（それ以前の検索は有料サービス）。
  目次の番号表記は「（国土交通一三一六）」のような略式で、「（同…）」は
  直前の発出者を指す。目次の各項目は「号のそのページのViewer」へのリンクで、
  本文の実体は号の全ページPDF（画像＋OCRテキスト層）。OCR層は空白除去で
  正規化すると告示見出しで切り出し可能だが、品質は原本確認が前提。
  改正告示は件名に根拠法令名が出ないため、被改正告示が台帳に既にある
  場合に取り込む第2ティアを設けた。初回実行（90日分）では24件を検出し、
  うち23件は他の2源に無い新規、1件（mlit-2026-1316）はweb源と統合された。
  総務省（消防法）の告示もこの源からのみ入った
- 官報サイトの利用ルール（2026-11-11確認）: コンテンツ自体は公共データ
  利用規約（PDL1.0）で出典明記により利用可だが、禁止事項に「検索ロボットや
  クローラによるデータ収集等の官報発行サイトに負荷をかける行為」の禁止が
  明記されている。本パイプラインの取得は週次・少量・間隔ありで負荷は
  人間の閲覧と同程度だが、文面上のグレーは残る。公開・運用拡大の前に
  運営（内閣府）への確認が望ましい

## 本文取得の実装上の注意（2026-11-11追記）

- **文字コード**: 国交省のSGML原文ページは `charset=shift_jis` 宣言のものが
  多い。UTF-8決め打ちで読むと文字化けし、34件が `no_text_found` になっていた。
  `build.decode_html` はmetaタグのcharsetを優先し、無ければ
  utf-8 → shift_jis → euc-jp の順に試して、タイトルが見つかるデコードを採用する。
- **短い告示**: 全文が400〜700字しかない告示がある（例: 建設省告示の指定系）。
  旧ルールの「800字超でなければ捨てる」では全文入りのページまで捨てていた。
  現在は200字超かつタイトルがページ内に含まれる場合に `page_text_short`
  として受け入れる。タイトルが無ければ一覧・エラー画面とみなして捨てる。
  この2点の修正で、本文取得は441/479件（92%）→ 475/479件（99%）になった。
  残る4件は、画像PDFでテキスト層が無い mlit-2020-821 と、官報PDFからの
  切り出しに失敗した3件（mlit-2026-117/1180/1181）。
- **台帳の維持**: 官報源は state に基づく増分取得のため、新規0件の実行では
  インベントリに過去の官報分が現れない。`run_all` は既存の台帳も統合の種に
  することで、既存レコードを維持する（これが無いと週次実行のたびに官報分が
  台帳から消える。2026-11-11に実際に23件が欠落し、state を90日前に戻して
  再スキャンすることで復旧した。復旧手順: `data/kanpo_state.json` の
  `last_checked` を90日前に書き戻して `run_all` を実行する。state は実行後に
  当日へ更新される）。
- **実行環境**: PyMuPDF が必要（`requirements.txt`）。無い環境ではPDFの
  テキスト抽出が `pdf_error:ModuleNotFoundError` になる。

## やらないこと（意図的に）

- 溶け込み（改正適用済み現行文の生成）: 上記の基準の問題として扱わない
- 現行性の判定（廃止済みか否か）: 一覧・ページ側に情報が無く、官報照合が必要
- 告示と法令条文のリンク付け: 本パイプラインは「集める」まで。
  リンクは利用側の課題として分離する

## ロードマップ候補

1. 官報との照合による母集団の確定（昭和期の薄さの検証を含む）。
   未来方向の継続収集は官報源＋週次実行で実施中（2026-11-11開始）。
   残るのは過去分の照合で、有料検索サービスの利用判断が要る
2. 改正関係の抽出（「○○の一部を改正する告示」から被改正告示への参照）
3. 他省庁所管の建築関係告示（消防庁など）への拡張
   （官報源からは総務省分が入り始めた。省庁別一覧のある源は未接続）
4. 差分公開（GitHub公開時のCI実行など）
